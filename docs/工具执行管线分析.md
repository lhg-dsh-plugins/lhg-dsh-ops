# DeepSeek Harness 工具执行管线完整技术分析

## 一、总体架构概览

DeepSeek Harness 的工具执行管线是一个分层、可插拔的瀑布(waterfall)管道系统，从模型返回 ToolCallBlock 到最终结果通知，经过五个核心阶段：**pre-execute → execute → tool body → post-execute → result**。

核心文件：
- `packages/core/tools/src/index.ts`（~1993行）— ToolRuntime 服务，管线定义与调度
- `packages/core/agent-loop/src/tool-calls.ts`（~300行）— executeToolCalls() 并行调度器
- 各插件包 — 瀑布事件的具体监听器

## 二、完整生命周期流程图

```
Agent Loop (agent.ts)
  Model Response → ToolCallBlock[] → executeToolCalls()
       │
       ▼
executeToolCalls() (tool-calls.ts)
  1. 解析 toolCalls → PlannedCall[]
  2. 按序遍历，executionMode() 判定 exclusive/parallel
  3. exclusive: 单独执行，形成屏障
     parallel: 全部入组，滚动并行池
  4. runGroup() 调度执行
       │ per tool call
       ▼
ToolRuntimeScheduler (TOOL_RUNTIME_SCHEDULER)
  prepare → dispatch → finalize → finish

═══════════════════════════════════════════════════════════════
                    详细管线展开
═══════════════════════════════════════════════════════════════

Stage 0: createExecution() — 创建执行对象
─────────────────────────────────────────
输入: ToolExecutionInput (callId, name, arguments, agent, signal, parent?)

1. 创建 ToolExecutionToken (Symbol 关联标识)
2. 解析 rootCallId
3. 检查 PTC 模式折叠 (collapses):
   - PTC 模式 + 模型直调非 run_code → final-result (UNKNOWN_TOOL + 路由提示)
   - 已取消 → final-result (ABORTED_BEFORE_DISPATCH)
4. snapshotJsonValue(exec.arguments) — 无损 JSON 快照 + deepFreeze
   - 快照失败 → final-result (错误)
5. 捕获 finalizeContent / projectContent 回调
6. 初始化 cancellationStates: { callerSignal, bodyInvoked: false }
7. 初始化 deferredContexts: []

输出:
  kind='ready'          → 进入 prepare 阶段
  kind='final-result'   → 跳到 finish 阶段
       │
       ▼
Stage 1: prepareExecution() — 预执行策略管线
────────────────────────────────────────────
1. callerCancelled 检查 → final-result (ABORTED_BEFORE_DISPATCH)
2. tools/pre-execute 瀑布 (waterfall)
   输入: (exec: ToolExecution, next)
   默认终值: { kind: 'allow' }
   决策: allow→继续 | deny→拒绝 | cancel→取消 | ask→人工审批
3. 若 ask → serviceAsk() — ApprovalService 交互
   allowed-once→allow | rejected/cancelled/unavailable→deny
   无 ApprovalService / 无 agent → 降级为 deny
4. approvalCancelled + callerCancelled → ABORTED_BEFORE_DISPATCH
5. cancel决策 → ABORTED_BEFORE_DISPATCH
6. guardReason() — 单调 Guard 检查 (全局→scope chain)
7. callerCancelled 再次检查

输出:
  kind='dispatch'     → 进入 dispatch 阶段
  kind='post-result'  → 进入 finalize 阶段
  kind='final-result' → 进入 finish 阶段
       │
       ▼
Stage 2: dispatchScheduledExecution() — 执行调度管线
────────────────────────────────────────────────────
1. tools/execute 瀑布 (waterfall)
   输入: (exec: ToolDispatchExecution, next)
   默认终值: dispatchToolBody(exec) 的结果
   监听器可替换 exec.signal，调用身份不可变

   dispatchToolBody() — 工具体执行:
   1. fuseToolSignals(callerSignal, wrapperSignal) — 融合取消信号
   2. 融合后信号已 abort → ABORTED_BEFORE_DISPATCH
   3. resolveExecution() → 未找到抛 ToolNotFoundError
   4. state.bodyInvoked = true
   5. tool.execute(args, exec) — 实际执行工具体
      exec 上可用: deferContext(context), concludeTurn()
   6. createSuccessResult():
      snapshotToolValue → validateJsonSchemaValue → output.render
      → output.presentationMeta → concludesTurn 标记
   7. 信号已 abort → toolAbortedResult (ABORTED)
   8. tool.execute 抛异常 → toolErrorResult(error)
   9. finally: fused.dispose() + 恢复 exec.signal

2. normalizeDispatchResult() — 规范化瀑布结果
3. 附加 deferredContexts 到 result.additionalContexts
4. callerCancelled 检查 (成功结果 → 替换为 ABORTED)

输出:
  kind='post-result'  → 进入 finalize 阶段
  kind='final-result' → 进入 finish 阶段 (管线异常)
       │
       ▼
Stage 3: finalizeScheduledExecution() — 后执行策略管线
──────────────────────────────────────────────────────
1. projectContent() — 工具定义的内容投影 (post-execute 之前)
2. tools/post-execute 瀑布 (waterfall)
   输入: (exec, result: Readonly<ToolExecutionResult>, next)
   默认终值: { kind: 'accept' }
   决策: accept(保留/替换content/替换value) | block(转为isError+feedback)
3. callerCancelled 检查 (成功结果 → ABORTED)
4. 传递给 finishScheduledExecution()
       │
       ▼
Stage 4: finishScheduledExecution() — 定稿与通知
────────────────────────────────────────────────
1. materializeFinalResult() — 第一次物化 (snapshotJsonValue + deepFreeze)
2. applyFinalContent() — finalizeContent 回调 (同步,不可抛异常)
3. materializeFinalResult() — 第二次物化 (含 finalizeContent 修改)
4. notifyResult() — 通知观察者
   Object.freeze(exec) → ctx.emit('tools/result', exec, result)
   观察者失败只记录日志，不影响结果

返回: ToolExecutionResult (深冻结的最终结果)
       │
       ▼
回到 executeToolCalls() — 结果提交
──────────────────────────────────
1. needsPost=true  → finalize() 再 finish()
   needsPost=false → 直接 finish()
2. appendToolResult() — 写入 Session 日志
3. additionalContexts → acceptContext() → 注入下一轮 inbox
4. concludesTurn → 标记轮次终结
```

## 三、executeToolCalls() 的调度逻辑

### 3.1 调度流程

```
executeToolCalls(ctx, turn, step, toolCalls, signal, acceptContext)
  │
  ├─ 解析 toolCalls → PlannedCall[] (每个含 block + exec)
  │   exec = { callId, name, arguments: parseArguments(raw), agent, signal }
  │
  ├─ 循环: next < planned.length
  │   ├─ executionMode(first) 判定
  │   │   exclusive → group = [first] (单元素屏障)
  │   │   parallel  → group = planned.slice(next) (剩余全部入组)
  │   │
  │   └─ runGroup(ctx, turn, step, group, mode, signal, acceptContext)
  │       ├─ fillPool(): 并行启动工具调用
  │       │   while (!aborted && nextToStart < group.length
  │       │          && inFlight.size < maxParallelToolCalls)
  │       │     - 重检后续调用的 executionMode
  │       │     - startCall(index):
  │       │       1. appendToolCall → session 日志
  │       │       2. scheduler.prepare(exec)
  │       │       3. dispatch/post-result/final-result
  │       ├─ Promise.race(inFlight) → 等待任一完成
  │       ├─ commitReady(): 按模型顺序提交结果
  │       └─ aborted: 未启动调用 → appendSkippedToolCall
  └─ 返回 { concluded }
```

### 3.2 exclusive vs parallel 分组

- **exclusive（排他）**: 未声明 `isConcurrencySafe`，或返回非 `true` → 单独执行，形成排序屏障
- **parallel（并行）**: `isConcurrencySafe(args) === true` → 可与兄弟调用重叠调度
- 运行时动态重分类: fillPool 在每次启动前重新检查 `executionMode`
- **maxParallelToolCalls**: 来自 `ctx.agentLoop.config.maxParallelToolCalls`

### 3.3 有序性保证

- **prepare（含 pre-execute）有序**: 一次只跑一个 pre-execute
- **dispatch（含 execute 瀑布 + tool body）可重叠**: 并行组中的调用同时执行
- **result 和 context 按模型顺序提交**: commitReady 严格按 committed 索引递增

## 四、ToolRuntime 各阶段详细分析

### 4.1 createExecution() — 执行对象创建

关键操作：
1. **PTC 折叠判定** (`collapses()`): PTC 模式下，模型直调（无 parent token）只能调 `run_code`，否则直接返回 `UNKNOWN_TOOL` 错误 + 路由提示
2. **参数物化**: `snapshotJsonValue(exec.arguments)` 确保无损 JSON + `deepFreeze` 冻结
3. **回调快照**: `finalizeContent` 和 `projectContent` 在参数物化前捕获
4. **取消状态初始化**: `cancellationStates` 记录原始 callerSignal 和 bodyInvoked 标志

### 4.2 prepareExecution() — 预执行策略

决策链路：
1. `callerCancelled` → `ABORTED_BEFORE_DISPATCH`
2. `tools/pre-execute` 瀑布 → `PreToolDecision`
3. `ask` → `serviceAsk()` → ApprovalService 交互
4. `cancel` → `ABORTED_BEFORE_DISPATCH`
5. `guardReason()` → 全局 + scope chain 的单调 guard 检查
6. 再次 `callerCancelled` 检查
7. 全部通过 → `dispatch`

### 4.3 dispatchScheduledExecution() — 执行调度

核心流程：
1. `tools/execute` 瀑布，以 `dispatchToolBody()` 为默认终值
2. `dispatchToolBody()`:
   - `fuseToolSignals()`: 融合 callerSignal + wrapperSignal
   - 融合后 abort → `ABORTED_BEFORE_DISPATCH`
   - `resolveExecution()` 查找定义 → 未找到抛 `ToolNotFoundError`
   - `state.bodyInvoked = true`
   - `tool.execute(args, exec)` — 实际执行
   - `createSuccessResult()`: 快照 → schema 校验 → render → presentationMeta → concludesTurn
   - 融合信号 abort → `ABORTED`（body 已启动）
   - finally: `fused.dispose()` + 恢复原始 signal
3. `normalizeDispatchResult()`: 规范化瀑布包装器的返回值
4. 附加 `deferredContexts`

### 4.4 finalizeScheduledExecution() — 后执行策略

1. `projectContent()`: 工具定义的内容投影（在 post-execute 之前）
2. `postExecute()`: `tools/post-execute` 瀑布
3. `callerCancelled` 检查
4. 传递给 `finishScheduledExecution()`

### 4.5 finishScheduledExecution() — 定稿与通知

1. `materializeFinalResult()`: 快照 + 冻结
2. `applyFinalContent()`: 执行 `finalizeContent` 回调（同步，不可抛异常）
3. 二次 `materializeFinalResult()`（含 finalizeContent 修改）
4. `notifyResult()`:
   - `Object.freeze(exec)`
   - `ctx.emit('tools/result', exec, result)`
   - 观察者失败只记日志，不影响结果

## 五、四大瀑布事件分析

### 5.1 tools/pre-execute 瀑布

**签名**: `(exec: ToolExecution, next: () => Promise<PreToolDecision>) => Promise<PreToolDecision>`

**决策类型 PreToolDecision**:
| kind | 含义 | 效果 |
|------|------|------|
| `allow` | 允许执行 | 继续到 guard 检查 |
| `deny` | 拒绝执行 | 返回错误结果 (reason + info) |
| `cancel` | 取消执行 | ABORTED_BEFORE_DISPATCH |
| `ask` | 请求审批 | 通过 ApprovalService 交互 |

**实际监听器**:
- **hooks-claude-code** (`packages/experimental/hooks-claude-code/src/index.ts`): 运行 PreToolUse 钩子 → deny/ask/allow

**关键语义**:
- `next()` 必须调用（瀑布语义），否则短接整条链
- 异步监听器必须观察 `exec.signal`

### 5.2 tools/execute 瀑布

**签名**: `(exec: ToolDispatchExecution, next: () => Promise<ToolExecutionResult>) => Promise<ToolExecutionResult>`

**可替换**: 仅 `exec.signal`（调用身份不可变）

**实际监听器**:

1. **timeout-policy** (`packages/guard/timeout-policy/src/index.ts`):
   - 读取 `tool.timeoutMs`，设置 deadline
   - 替换 `exec.signal` 为 deadline signal
   - 执行后若本插件超时 → 替换结果为 `TOOL_TIMEOUT` 错误
   - finally 恢复上游 signal

2. **session-checkpoint-policy** (`packages/session/session-checkpoint-policy/src/index.ts`):
   - 顶级工具调用前 `sessions.flush()` 确保持久化
   - flush 后若信号已 abort → `ABORTED_BEFORE_DISPATCH`

3. **browser-use-runtime** (`packages/experimental/browser-use-runtime/src/mcp.ts`):
   - MCP 浏览器工具的执行包装

4. **claude-code-mods** (`packages/experimental/claude-code-mods/src/index.ts`):
   - Claude Code 风格的 turn.start/tool.call 事件包装

5. **computer-use-cua-driver-native** (`packages/experimental/computer-use-cua-driver-native/src/index.ts`):
   - 计算机使用工具的执行包装

**信号融合机制** (`fuseToolSignals`):
- 创建新 AbortController
- 监听 callerSignal 和 wrapperSignal 的 abort 事件
- 任一 abort → 控制器 abort + 清理监听
- dispatch 结束时 dispose 清理

### 5.3 tools/post-execute 瀑布

**签名**: `(exec: ToolExecution, result: Readonly<ToolExecutionResult>, next: () => Promise<PostToolDecision>) => Promise<PostToolDecision>`

**决策类型 PostToolDecision**:
| kind | 含义 | 效果 |
|------|------|------|
| `accept` | 接受结果 | 可选替换 content 或 value，附加 additionalContexts |
| `block` | 阻止结果 | 转为 isError，feedback 替代内容 |

**accept 的三种变体**:
- 保留 content: `{ kind: 'accept' }` 或 `{ kind: 'accept', content: undefined }`
- 替换 content: `{ kind: 'accept', content: ContentBlock[] }`（如 spill-policy 截断长输出）
- 替换 value: `{ kind: 'accept', value: JsonValue }`（重新渲染，不可用于失败结果）

**block 的语义**:
- 结果变为 `isError: true`，content 为 decision.feedback
- 工具体附加的 additionalContexts 被丢弃
- 只有 block 决策显式提供的 additionalContexts 保留

**实际监听器**:

1. **spill-policy** (`packages/spill/spill-policy/src/index.ts`):
   - Token 预算约束：超过 maxInlineTokens 的结果被截断
   - 保留头尾 + 省略提示 + spill 文件引用
   - 失败时降级保留原内容

2. **repeat-tool-reminder** (`packages/guard/repeat-tool-reminder/src/index.ts`):
   - 检测连续重复调用（相同工具名 + 规范化参数）
   - 达到阈值时注入提醒 additionalContext
   - 不 veto/rewrite，只是建议性注入

3. **hooks-claude-code** (`packages/experimental/hooks-claude-code/src/index.ts`):
   - PostToolUse 钩子 → block (feedback) 或 accept + context

4. **hooks-codex** (`packages/experimental/hooks-codex/src/index.ts`):
   - Codex 风格的 PostToolUse 钩子

5. **tool-fs-search (grep/glob)** (`packages/fs/tool-fs-search/src/`):
   - 搜索结果超过上限时截断 + spill 文件

### 5.4 tools/result 通知

**签名**: `(exec: Readonly<ToolExecution>, result: Readonly<ToolExecutionResult>) => undefined`

**模式**: emit（单向通知，不可修改结果）

**调用时机**: `finishScheduledExecution()` 中，exec 已 `Object.freeze()`，result 已 deepFreeze

**实际监听器**:

1. **tool-present** (`packages/deliverables/tool-present/src/index.ts`):
   - `present` 工具成功后，在 session 中记录 `deliverables/presented` 事件

2. **agent-instructions** (`packages/context/agent-instructions/src/index.ts`):
   - 追踪工具执行触碰的文件路径，在 result 后投影指令更新
   - PTC 子调用的 touches 冒泡到父执行

3. **subagent/structured** (`packages/subagent/subagent/src/structured.ts`):
   - 捕获结构化输出工具的返回值
   - 直调和 PTC 子调用两种路径分别处理

4. **claude-code-mods** (`packages/experimental/claude-code-mods/src/index.ts`):
   - 清理 token → 替换映射

## 六、中止(abort)和取消(cancel)的处理路径

### 6.1 两条取消来源

| 来源 | 标识 | 说明 |
|------|------|------|
| callerSignal | `exec.signal` | 调用方提供的 AbortSignal（通常是 agent-loop 的 step signal）|
| wrapperSignal | execute 瀑布替换 | timeout-policy 等插件注入的 deadline signal |

### 6.2 取消检查点

```
createExecution
  ├─ PTC折叠前: signal.aborted → ABORTED_BEFORE_DISPATCH (final-result)

prepareExecution
  ├─ 创建后: callerCancelled → ABORTED_BEFORE_DISPATCH (final-result)
  ├─ pre-execute后: approvalCancelled + callerCancelled
  │                 → ABORTED_BEFORE_DISPATCH (post-result)
  ├─ cancel决策 → ABORTED_BEFORE_DISPATCH (post-result)
  ├─ guard后: callerCancelled → ABORTED_BEFORE_DISPATCH (post-result)

dispatchScheduledExecution
  ├─ dispatchToolBody:
  │   ├─ fusedSignal.aborted → ABORTED_BEFORE_DISPATCH (body 未启动)
  │   ├─ bodyInvoked = true
  │   ├─ tool.execute() 后 signal.aborted → ABORTED (body 已启动，丢弃成功结果)
  │   ├─ tool.execute() 抛异常 → toolErrorResult (保留工具自身错误)
  ├─ dispatch后: callerCancelled && !isError → cancellationResult

finalizeScheduledExecution
  ├─ postExecute后: callerCancelled && !isError → cancellationResult

finishScheduledExecution
  │  (无取消检查 — 结果已经定型)

executeToolCalls (tool-calls.ts)
  ├─ fillPool: signal.aborted → aborted = true
  ├─ Promise.race 后: signal.aborted → aborted = true
  ├─ aborted: 未启动调用 → appendSkippedToolCall (ABORTED_BEFORE_DISPATCH)
```

### 6.3 取消语义区分

| 错误码 | 含义 | bodyInvoked | additionalContexts |
|--------|------|-------------|-------------------|
| `ABORTED_BEFORE_DISPATCH` | body 未启动 | false | 保留 prior 的 |
| `ABORTED` | body 已启动但被取消取代 | true | 保留 prior 的 |

**关键不变量**: 已启动的 tool.execute() Promise 不会被放弃——注册表等待其到达静止(quiescence)后再用 ABORTED 替换成功结果。工具体内部的错误优先于取消（工具自身错误不会被取消覆盖）。

### 6.4 信号融合细节

`fuseToolSignals(caller, wrapper)`:
- caller === wrapper → 直接使用（无需融合）
- 否则创建 AbortController，监听两个信号的 abort 事件
- 任一触发 → 控制器 abort + 立即清理监听器
- 返回 `{ signal, dispose }` 供 dispatch 结束时清理

注册表在 dispatchToolBody 的 finally 中恢复原始 wrapperSignal，确保 post-execute 监听器永远看不到 timeout 插件的已-abort 信号。

## 七、调度器与 ToolRuntime 的协作

### 7.1 ToolRuntimeScheduler 接口

```typescript
interface ToolRuntimeScheduler {
  prepare(exec: ToolExecutionInput): Promise<ScheduledToolPreparation>
  dispatch(exec: ToolRunContext): Promise<ScheduledToolDispatch>
  finalize(exec: ToolRunContext, result: ToolExecutionResult): Promise<ToolExecutionResult>
  finish(exec: ToolRunContext, result: ToolExecutionResult): ToolExecutionResult
}
```

agent-loop 的 executeToolCalls() 通过 `ctx.tools[TOOL_RUNTIME_SCHEDULER]` 访问此接口：
- **prepare 有序**: pre-execute 瀑布必须串行
- **dispatch 可重叠**: execute 瀑布 + tool body 可并行
- **finalize/finish 有序**: 结果按模型顺序提交

### 7.2 ScheduledToolPreparation 三种结果

| kind | 含义 | 后续 |
|------|------|------|
| `dispatch` | 通过所有前置检查 | → dispatch() |
| `post-result` | 有结果但需 post-execute | → finalize() |
| `final-result` | 最终结果，跳过 post-execute | → finish() |

### 7.3 execute() 的完整调度路径

`ToolRuntime.execute()` 使用 `prepareExecution()` + `completeScheduledExecution()` 串联：

```typescript
async execute(exec: ToolExecutionInput): Promise<ToolExecutionResult> {
  return this.prepareExecution(exec, prepared =>
    this.completeScheduledExecution(prepared)
  )
}

private async completeScheduledExecution(prepared: ScheduledToolPreparation) {
  switch (prepared.kind) {
    case 'dispatch': {
      const dispatched = await this.dispatchScheduledExecution(prepared.exec)
      return dispatched.kind === 'post-result'
        ? await this.finalizeScheduledExecution(prepared.exec, dispatched.result)
        : this.finishScheduledExecution(prepared.exec, dispatched.result)
    }
    case 'post-result':
      return await this.finalizeScheduledExecution(prepared.exec, prepared.result)
    case 'final-result':
      return this.finishScheduledExecution(prepared.exec, prepared.result)
  }
}
```

## 八、数据流关键类型

### 8.1 ToolExecutionResult

```typescript
type ToolExecutionResult = ToolExecutionSuccess | ToolExecutionFailure

interface ToolExecutionSuccess {
  readonly isError: false
  readonly value: JsonValue        // 执行局部规范值，不写入持久日志
  readonly content: ContentBlock[] // 模型可见的渲染投影
  readonly error?: never
  readonly meta?: JsonValue        // UI 演示元数据
  readonly additionalContexts?: UserMessage[]
  readonly concludesTurn?: true    // 终结当前轮次
}

interface ToolExecutionFailure {
  readonly isError: true
  readonly error: ToolFailure
  readonly value?: never
  readonly content: ContentBlock[]
  readonly meta?: JsonValue
  readonly additionalContexts?: UserMessage[]
  readonly concludesTurn?: never   // 失败不终结轮次
}
```

### 8.2 关键错误类型

| 错误类 | code | 场景 |
|--------|------|------|
| ToolNotFoundError | UNKNOWN_TOOL | 工具名不可见或被 PTC 折叠 |
| ToolOutputError | INVALID_TOOL_OUTPUT | 工具返回值违反 output schema |
| TOOL_ABORTED | ABORTED | body 已启动后被取消 |
| TOOL_ABORTED_BEFORE_DISPATCH | ABORTED_BEFORE_DISPATCH | body 未启动即被取消 |
| TOOL_TIMEOUT | TOOL_TIMEOUT | timeout-policy 的 deadline 到期 |

## 九、设计要点总结

### 9.1 不变量

1. **无损 JSON**: 所有跨越管线边界的数据（arguments、value、content、meta）都必须是 `snapshotJsonValue` + `deepFreeze` 的无损 JSON
2. **瀑布必须 next()**: 三个瀑布事件中，`next()` 必须被调用，否则短接后续链
3. **Guard 单调性**: 任一 guard 拒绝即终止，不允许覆盖其他 guard 的拒绝
4. **取消不放弃**: 已启动的 Promise 必须等其到达静止，不会被硬杀
5. **结果不可变**: finish 阶段后的结果深冻结，tools/result 观察者无法修改

### 9.2 分层设计

- **pre-execute**: 可扩展的策略层（allow/deny/cancel/ask），由插件注册
- **guard**: 注册表内置的单调检查，在 pre-execute 之后，优先级更高
- **execute**: around 模式包装，可替换 signal 但不能改变调用身份
- **post-execute**: 可扩展的结果策略层（accept/block），由插件注册
- **finalizeContent**: 工具定义私有的终稿回调，最后的内容修改机会
- **projectContent**: 工具定义的内容投影，在 post-execute 之前运行
- **tools/result**: 单向通知，观察者不可修改结果

### 9.3 调度器设计要点

- prepare 有序、dispatch 可重叠、result 按序提交
- exclusive 工具形成排序屏障，parallel 工具共享并行池
- maxParallelToolCalls 限制并行度
- 运行时动态重分类：每次启动前重检 executionMode
- Abort 停止启动新调用，等待已启动调用完成，未启动调用记录合成结果

### 9.4 PTC 模式特殊性

- PTC 模式下模型只能直调 `run_code`，其余工具通过 SDK 内部调度
- 折叠拒绝发生在 createExecution 阶段，早于 pre-execute
- 折叠拒绝携带路由提示，告知模型改用 `run_code`
- PTC 子调用通过 parent token 关联到外层 run_code 执行

### 9.5 核心并发设计洞察

管线被拆分为 4 个调度器阶段（prepare/dispatch/finalize/finish），这是核心并发设计：
- **prepare 串行**：确保 pre-execute 瀑布的决策顺序可预测
- **dispatch 并行**：允许多个工具的 execute 瀑布 + body 同时运行
- **finalize/finish 按序**：保证模型看到的结果顺序与 ToolCallBlock 中的顺序一致
- 这种设计在安全性和性能之间取得了平衡：策略检查不并发，执行可以并发，结果有序
